灵衢总线「多对多通信」
软硬件架构 · 结构 · 流程 · 拓扑 交互图解

灵衢（UnifiedBus, UB）用单一协议栈统一「内存访问 / 消息传递 / 过程调用 / 资源管理」，并把「任意 UBPU 平等直访 任意 UBPU」的多对多通信做成了一种体系能力。本页以 SVG 交互图呈现其协议栈、单芯片硬件、Jetty 多对多编程模型、 事务流转时序、UMMU 寻址鉴权，以及 nD-Mesh / Clos / Torus 三类大规模拓扑。

01协议栈分层

灵衢用单一协议栈承载内存 / 消息 / 调用 / 管理四类操作。多对多通信的正交分工是—— 网络层路由（多路径）、传输层通道共享（多通道汇聚）、事务层 Jetty/SQ/RQ（连接池化）、 功能层 M2N（多对多语义）。旁路单元 UMMU 负责地址转换与鉴权，UBFM 负责域级资源管理。

02硬件结构：单芯片互联与 On-Chip Switch

昇腾 950 采用 2×AI Die + 2×IO Die + 高速片上内存 的 Chiplet UMA 架构。关键设计是 UB On-Chip Switch 内嵌于 IO Die：片间转发流量在 IO Die 完成，不进计算 Die、不占 DRAM 带宽—— 这正是密集多对多流量不会拖垮 AI 算力的硬件原因。

03软件模型：Jetty 多对多（M2N）通信

规范 §8.2.2.2 给出灵衢对「多对多」的精确定义：Initiator Jetty 与 Target Jetty 无一一绑定， 任一 Initiator 可发任意 Target，任一 Target 可收任意 Initiator。相比 1:1 模型的 O(N²) 连接对象，M2N 把 Jetty 数量降到 O(N)， 用「事务包内显式携带对端 Jetty ID + 响应回带发起方 ID」换连接资源池化。

06CCU 与 UB 的详细关系

一个必须先厘清的边界：CCU 不在《灵衢®基础规范》里。UB 规范 §8.6 用「集合通信操作」这个 功能层语义描述它——「一次集合通信可被抽象为单一功能调用，再由 UB 分解为多个底层 UB 事务，动态映射到各 UBPU 协同执行」。 CCU（Collective Communication Unit）则是昇腾 950 芯片把这条语义具体化的硬件单元。因此二者的关系是： UB 定义「集合通信是什么」，CCU 实现「集合通信怎么用 UB 跑」——CCU 的数据面直接复用了 URMA 的 Jetty/SQ-RQ/UMMU/传输层。

死锁避免（§5.3.6）：Mesh/Torus 存在环，信用流控逐级反压可能形成循环依赖。规范给出三手段—— ① 路由防死锁（拓扑特定路由算法）② VL 主动切换（配置 Input VL→Output VL 映射破除环路）③ 超时丢包（队列超时未调度即丢包解环）。 Torus 因此特别依赖「维度序路由（dimension-order routing）+ VL 切换」来保证无死锁。
组播说明：网络层只有单播路由（Primary/Port CNA），无硬件组播交付。「广播/组播」在 §8.6 是以 多 Entity 协同·融合操作 的形式由软件/微码组合实现。多对多扇出场景由 CCU（Broadcast/AllGather）硬件加速，属「操作级扇出」而非「地址级组播」。
